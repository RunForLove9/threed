# Threed 3D 技术底座 Constitution

## Core Principles

### I. 平台优先（Platform-First）

本仓库是统一的 3D 组件、物品、环境生成技术底座，不是业务应用。

- 所有能力 MUST 以版本化、有文档的 API / SDK 形式对外暴露；未进入公共 API 的能力
  属于内部实现，不承诺任何稳定性。
- 业务层概念（具体业务场景、业务流程、业务文案）MUST NOT 进入底座代码；底座只
  提供通用原语：物品设计、编辑、调整、交互、环境交互、环境设计等。
- 底座 MUST 能在无任何业务接入的情况下独立运行、独立测试、独立演示。

**理由**: 底座的价值取决于 API 的稳定性与通用性；业务逻辑一旦渗入，公共 API 面即
不可控，此后每个业务变更都会变成底座变更。

### II. Three.js 单一渲染内核（Single Rendering Core）

three.js 是本底座唯一认可的渲染与场景图内核。

- 渲染、场景图、空间计算能力 MUST 构建于 three.js 之上；MUST NOT 引入第二套渲染
  引擎（Babylon、裸 WebGL/WebGPU 直写等），除非通过宪法修订明确批准。
- three.js 依赖版本由底座集中锁定与升级；仓库内 MUST NOT 出现多个版本共存。
- 对外 API 优先暴露平台自身的抽象；同时 MUST 提供显式标注的 three.js 逃生舱
  （escape hatch）满足高级需求，MUST NOT 隐式、间接地泄漏内核对象。

**理由**: 单一内核使封装、升级与性能优化只需做一次；受控逃生舱让高级用户不必绕开
平台，同时保留兜底路径。

### III. 数据驱动与可序列化（Data-Driven & Serializable）

场景与内容是数据，渲染只是数据的投影。

- 组件、物品、环境的定义 MUST 是声明式、可序列化的数据描述（可持久化、可网络
  传输、可版本比对）。
- 通过 API/SDK 完成的任何创建、编辑、调整 MUST 可完整表达为数据变更；任一场景
  状态 MUST 能仅凭序列化数据重建，MUST NOT 依赖隐藏的运行时状态。
- 序列化格式 MUST 有明确的 schema 与版本号；格式变更 MUST 保持向后兼容或提供
  迁移工具。

**理由**: API 驱动的生成/编辑/交互，前提是一切状态可表达为数据；可序列化也是协同
编辑、回放、资产复用等一切上层能力的地基。

### IV. 可组合组件体系（Composable Component System）

一切内容皆组件，组件注册表是底座的核心资产。

- 物品、环境、交互行为、生成器 MUST 实现为自包含、可复用、可嵌套组合的组件。
- 每个组件 MUST 有明确的输入契约（props/参数）与输出语义，并 MUST 在组件注册表
  注册后方可被公共 API 引用。
- 组件 MUST 能脱离具体场景独立测试（含渲染冒烟测试）。

**理由**: 组件化是「统一底座」承诺的落点——物品设计与环境设计共享同一套组合、
复用、演化机制，能力才能沉淀复利。

### V. 契约测试与测试先行（Test-First & Contract Testing）——不可协商

- 核心能力开发遵循 TDD：先写测试、确认失败、再实现（Red-Green-Refactor 循环）。
- 每个公共 API/SDK 面 MUST 有自动化契约测试；契约变更 MUST 同步更新测试与文档，
  并按语义化版本规则升版本。
- 渲染结果 MUST 有确定性验证手段：无头渲染冒烟测试 + 快照/黄金图片比对（带容差），
  确保 three.js 升级或重构后画面不发生未预期漂移。

**理由**: 底座的每次升级会同时作用于所有业务方；没有契约测试与渲染回归，升级本身
就是高风险动作。

## 技术约束（Technology Constraints）

- 渲染内核：three.js。具体版本在首次搭建时锁定；升级 MUST 集中进行并通过全量渲染
  回归测试。
- 语言与类型：核心代码使用 TypeScript；公共 API 的类型定义是契约的一部分，MUST
  随 SDK 一同发布。
- 运行环境：底座核心 MUST 同时支持浏览器与无头（headless）环境；无头能力是自动化
  测试与潜在服务端渲染的前提。
- 依赖最小化：新增运行时依赖 MUST 论证必要性；MUST NOT 引入与 three.js 能力重复
  的依赖。
- 性能：底座 MUST 内建基础性能度量（帧率、draw call、三角形数、显存/内存）。性能
  预算（v1.1.0 量化写回，实测基线见 `docs/perf-baseline.md`）：标准测试场景
  （`fixtures/standard-scene.json`）在 CI 管线 MUST 满足 **fps ≥ 30**（SwiftShader
  软件渲染基线；GPU 环境按 ≥ 55 另测）、**draw calls ≤ 8**、空场景 60 秒泄漏冒烟
  **jsHeap 增幅 ≤ 10%**。预算语义为 CI 断言而非硬拒绝——超标即渲染回归门禁失败，
  走性能归因。

## 开发工作流（Development Workflow）

- 规格驱动：功能 MUST 先撰写规格（Spec Kit 流程）再实现；与宪法的冲突 MUST 在
  specify 阶段暴露并解决，而非留到实现阶段。
- API 评审：新增或变更公共 API/SDK 面 MUST 先评审 API 设计（命名、版本影响、
  序列化影响、是否必须开逃生舱），评审通过后方可实现。
- 质量门禁：合并前 MUST 通过类型检查、单元测试、契约测试与渲染回归测试。
- 文档门禁：公共 API 变更 MUST 同步更新使用文档与可运行示例。

## Governance

- 本宪法是本仓库最高治理文件；其他实践与宪法冲突时，以宪法为准。
- 修订流程：修订 MUST 通过独立提交完成，提交说明中注明宪法版本变化与理由；涉及
  原则删除或重新定义（MAJOR）时 MUST 附迁移计划。
- 版本策略：宪法版本遵循语义化版本——MAJOR：原则删除或向后不兼容的重定义；
  MINOR：新增原则或实质性扩展指引；PATCH：澄清与措辞修正。
- 合规审查：每个 PR 描述 MUST 声明与宪法原则的关系（符合/不涉及），评审人 MUST
  核对该声明；新增运行时依赖与公共 API 变更 MUST 在 PR 中显式标注。
